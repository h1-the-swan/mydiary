# mydiary never deletes Joplin resources

mydiary uploads photos and maps to Joplin as resources but never deletes one, not even when a note stops using it or an edit fails after uploading it. A photo removed from a day, a replaced map, and an upload left over from a failed edit all stay in Joplin. When the same bytes are added again, `NoteEdit.add_resource` finds the resource through `resource_exists` and reuses it.

The reason is how Joplin's sync handles deletions, checked against the `@joplin/lib` 3.7.1 source. Deleting an item through the Data API records it in the client's `deleted_items` table. Saving an item with the same id again doesn't clear that record, and the sync's delete step (`syncDeleteStep`), which runs before uploads, deletes the item and its file on the sync target without checking whether it exists locally again. Every other device then deletes its copy. mydiary's resource ids are the md5 of the bytes, so deleting a resource and adding the same bytes back before the deleting client's next sync loses the resource everywhere, and the note is left with a broken image. A run against a throwaway pair of Joplin CLI profiles on 2026-11-21 showed exactly this for a photo removed from a note and added back 5 s later. The desktop app syncs soon after each change, which kept the window small. mydiary is moving to a headless Joplin client that syncs a minute after its previous sync finishes, which makes the window a minute or more.

Two other fixes were considered. Deferring deletes for a few minutes only moves the window, because adding the photo back just after the deferred delete runs loses it the same way. Giving each upload a fresh id would avoid reused ids altogether, but it changes the `JoplinPort.create_resource` contract and loses the sharing that depends on it: the same photo on two days is one resource.

## Consequences

- `JoplinPort` has no method for deleting a resource, and neither does `InMemoryJoplin` in the tests, so a call to one fails the tests. `MyDiaryJoplin.delete_resource` in `joplin_connector.py` remains only for cleaning up after `external_api` tests, and those tests delete a resource only when they uploaded bytes unique to that run, so its id never comes back. A test that uploads a fixed file leaves the resource in Joplin and reuses it on its next run.
- Resources nothing uses accumulate in Joplin. The desktop app's orphan cleanup (`ResourceService.deleteOrphanResources`) removes those no note has referenced for its "Keep note history for (days)" setting, 90 by default. It runs only where the desktop app runs. A re-add within that period reuses the resource.
- That cleanup skips a resource the desktop app only received through sync and never saw attached to a note: an upload from a failed edit that was never retried, or a map or photo replaced again before the desktop app synced the note in between. Those stay for good. If the space ever matters, a mydiary sweeper that removes only resources no Note Mirror body has referenced for weeks would keep any re-add race negligible.
- When the Joplin app's autosave writes a stale copy of a note back over an edit, the resources that copy shows still exist.
